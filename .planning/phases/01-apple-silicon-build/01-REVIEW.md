## Summary

Scope is the diff `0ae5e5cf..HEAD` on `default.rave`, `configure`, and
`README.md`: the Homebrew prefix lookup in `configure`, the `APP_MIN_OS`
change from `10.12` to `26.7.1`, and the README Building section.

What was checked directly on this machine:

- `brew list --versions` matches the six versions in the README block.
- `boost/crc.hpp`, `boost/variant.hpp`, `capnp/message.h`,
  `capnp/serialize-packed.h`, `sparsehash/dense_hash_map`,
  `libcapnp.dylib`, and `libkj.dylib` all exist under `/opt/homebrew`.
- `sh -n` and `bash -n` pass on `configure`.
- `local.rave` is in `.gitignore`.
- `APP_MIN_OS` reaches `Info.plist` through `PLIST_FLAGS`
  (`Applications/TextMate/Info.plist:32`).
- In a scratch copy of `configure`, a pre-existing `local.rave` with
  `/usr/local` was kept as-is with no prefix check (CR-01).
- In a scratch copy, a failing `brew` silently fell back to
  `/opt/homebrew` (WR-01).

The Homebrew logic works on the intended Apple Silicon path. The main defect
is that the new lookup is skipped entirely when a `local.rave` already exists,
which is the state of every existing checkout.

## Critical Issues

### CR-01: Existing `local.rave` silently bypasses the Homebrew lookup and keeps stale `/usr/local` flags

**File:** `configure:26-27` (with the write block at `configure:45-46`)
**Issue:** The whole prefix lookup and all header/dylib checks sit inside the
`else` of `if [[ -e local.rave ]]`. Any checkout that already has a
`local.rave` generated by the pre-change `configure` still contains
`add FLAGS "-I/usr/local/include"` and `add LN_FLAGS "-L/usr/local/lib"`. On
Apple Silicon, re-running `./configure` prints only
`Skipping writing ‘local.rave’: File already exists`, exits 0, and leaves the
stale paths in place. The build then fails later with unrelated
`capnp/message.h not found` style errors. The skip message suggests the
configuration is fine. Reproduced in a scratch copy: a `local.rave` containing
the `/usr/local` line was left unchanged, and no prefix check ran. This also
means `grep -c /usr/local local.rave` can print non-zero after a successful
`./configure`, contrary to the BUILD-02 acceptance intent. The phase's
clean-checkout test does not exercise this path.
**Fix:** Validate an existing `local.rave` instead of skipping silently. Fail
fast when it points at a prefix other than the one just detected:

```sh
if [[ -e local.rave ]]; then
	if grep -q '/usr/local' local.rave; then
		error "*** ‘local.rave’ points at /usr/local. Delete it and re-run ./configure."
	fi
	echo >&2 "Skipping writing ‘local.rave’: File already exists"
else
```

Alternatively, regenerate the file when it contains only the two lines this
script writes. Do not overwrite a hand-edited `local.rave` without asking.

## Warnings

### WR-01: `brew --prefix` failure is masked; the script silently falls back to `/opt/homebrew`

**File:** `configure:19-24`
**Issue:** `prefix="$(brew --prefix 2>/dev/null)"` discards brew's stderr and
ignores its exit status. If `brew` is installed but broken, the script
continues with `/opt/homebrew` and prints nothing. Reproduced with a failing
`brew` stub: the script wrote `-I/opt/homebrew/include` without any warning.
On an Intel Mac whose brew lives in `/usr/local`, the same failure produces
header errors that point at `/opt/homebrew` and suggest `brew install boost`,
which sends the user in the wrong direction. The fallback should apply only
when `brew` is absent.
**Fix:**

```sh
prefix=""
if which -s brew; then
	prefix="$(brew --prefix)" || error "*** ‘brew --prefix’ failed. Run: brew doctor"
elif [[ -d /opt/homebrew ]]; then
	prefix="/opt/homebrew"
fi
[[ -n "$prefix" ]] || error "*** Homebrew not found. Install it from https://brew.sh"
```

### WR-02: README documents MacPorts, but `configure` only supports Homebrew prefixes and tells MacPorts users to run `brew`

**File:** `README.md:32-39` (against `configure:10, 31, 35, 38, 42`)
**Issue:** The README still says the dependencies can be installed "using
either Homebrew or MacPorts", and it gives a `sudo port install` line. The
checks now look only under `brew --prefix` (or `/opt/homebrew`) and only at
Homebrew-style paths. A MacPorts user (`/opt/local`) gets a hard failure with
`Install with: brew install …`. The README does not mention that limitation.
**Fix:** Either state in the README that `configure` requires Homebrew, or
keep MacPorts working by also checking `/opt/local` (or accepting a prefix
override). Make the hint text match the install method the user actually has.

### WR-03: README Building section still gives the Intel-era `/usr/local/bin` PATH example

**File:** `README.md:68`
**Issue:** The example `$PATH:/usr/local/bin` is the path the old `configure`
targeted. On the Apple Silicon build this phase targets, Homebrew installs
`ninja` and `ragel` under `/opt/homebrew/bin`. A reader following the example
will not get the tools into the in-app build. This line sits in the same
section the phase is meant to fix.
**Fix:** Change the example to `$PATH:/opt/homebrew/bin`, or say
"`$(brew --prefix)/bin` (typically `/opt/homebrew/bin` on Apple Silicon)".

### WR-04: README says `./configure` "simply checks" dependencies, but it now writes `local.rave`

**File:** `README.md:62`
**Issue:** The paragraph says `./configure` "simply checks that all
dependencies can be found" and then calls `bin/rave`. The script now also
writes `local.rave` with `-I`/`-L` flags derived from `brew --prefix`, falls
back to `/opt/homebrew`, and skips writing if `local.rave` already exists. None
of that is documented, so a user who hits CR-01 has nothing to go on.
**Fix:** Replace the sentence with a description of the actual behavior, for
example: "`./configure` checks the dependencies under `$(brew --prefix)`
(falling back to `/opt/homebrew`), writes their include and library paths to
`local.rave` if that file does not exist, and then calls `bin/rave`. To change
the prefix, edit `local.rave`."

### WR-05: Platform floor changed to macOS 26.7.1 with no README requirement, no SDK check, and no stated compatibility impact

**File:** `default.rave:1` (flows to `default.rave:14, 16, 21, 25` and
`Applications/TextMate/Info.plist:32`)
**Issue:** `APP_MIN_OS` moves from `10.12` to `26.7.1`. This sets
`-mmacosx-version-min`, `--minimum-deployment-target` for `actool`/`ibtool`,
and `LSMinimumSystemVersion` in the built `Info.plist`. The effect is that the
built app will not launch on macOS 26.0 through 26.7.0 or on any earlier
release. The README does not state the new floor or the required SDK and
Xcode, even though the ROADMAP's build environment is macOS 26.7.1 with
Xcode 27.1. Nothing in `configure` or `default.rave` checks that the installed
SDK is at least `26.7.1`. Neither the README nor `configure` says anything
about the value being a hard-coded point release that must be bumped by hand.
This is an intentional change per BUILD-04, so it is not classified as a
blocker, but the requirement is invisible to anyone building or distributing
the app. The release-only `local-orig.rave` also emits
`os (>= ${APP_MIN_OS})` as a package dependency, so the published metadata
changes too.
**Fix:** Add a "Requirements" bullet to the README Setup section with macOS
and Xcode versions and the resulting minimum OS. In `configure`, assert the
SDK:

```sh
sdk="$(xcrun --sdk macosx --show-sdk-version 2>/dev/null)"
[[ -n "$sdk" ]] || error "*** Xcode command line tools not found."
```

Consider comparing `$sdk` against `APP_MIN_OS` and failing when the SDK is
older. Also update `.planning/codebase/ARCHITECTURE.md:248` (see IN-06).

## Info

### IN-01: `[[ ]]` used in a `#!/bin/sh` script; shellcheck SC3010 on new line 22

**File:** `configure:22` (also pre-existing at `configure:26, 53`)
**Issue:** The shebang is `/bin/sh`, but the script uses bash-only `[[ ]]`.
It works on macOS because `/bin/sh` is bash 3.2 in POSIX mode, but it breaks
on dash and other POSIX shells. The new line 22 adds another instance.
Shellcheck reports SC3010 for lines 22, 26, and 53, and SC2112 for the
`function` keyword on line 3. Lines 3, 26, and 53 are pre-existing.
**Fix:** Use `[ -z "$prefix" ]` and `[ -e local.rave ]`, or change the shebang
to `#!/bin/bash` to match the `bash.md` standard.

### IN-02: `echo >> local.rave` and `function error ()` do not follow project shell standards

**File:** `configure:45-46, 3`
**Issue:** `bash.md` asks for `printf` over `echo`, because `echo` handles
arguments and escapes inconsistently. The new `local.rave` lines are written
with `echo`. The `function` keyword is non-POSIX (SC2112). Also pre-existing
and out of diff scope: `$builddir` on line 53 is referenced but never set
(SC2154). The script runs with `set -u` commented out, so this becomes an
empty-string `bin/rave` invocation without an error.
**Fix:**

```sh
printf >>local.rave 'add FLAGS    "-I%s/include"\n' "$prefix"
printf >>local.rave 'add LN_FLAGS "-L%s/lib"\n' "$prefix"
```

### IN-03: Redundant submodule step in the README clone example

**File:** `README.md:56-58`
**Issue:** `git clone --recursive` already initializes submodules. The next
line, `git submodule update --init --recursive`, is redundant in this example
(it is still useful for an existing clone without `--recursive`). The
preceding sentence also tells the user to make sure they have a full checkout,
so the example reads as if the step is needed after cloning.
**Fix:** Drop the `git submodule update` line from the clone example, and
move it to a note for existing clones: "If you cloned without `--recursive`,
run `git submodule update --init --recursive`."

### IN-04: Tools are checked on `PATH` but headers and libraries are checked under `brew --prefix`

**File:** `configure:9-11, 19-24, 30-43`
**Issue:** `capnp`, `ninja`, `ragel`, and `multimarkdown` are found on `PATH`,
while the headers and dylibs come from `$prefix`. If `PATH` resolves `capnp`
to a different install (for example `/usr/local/bin/capnp` left over from an
Intel setup), the checks can pass against a mixed installation.
**Fix:** Optional. Verify that `$(command -v capnp)` is under `$prefix/bin`,
or print the resolved paths so the user can see which install is used.

### IN-05: Prefix is interpolated into `local.rave` without validation

**File:** `configure:45-46`
**Issue:** `$prefix` is written into a rave-syntax file without quoting or
validation. A prefix containing `"`, `$`, or whitespace would corrupt
`local.rave` or change what rave parses. `brew --prefix` normally returns a
safe path, and the user controls the environment, so the risk is low.
**Fix:** Reject prefixes that do not match a safe-character pattern, for
example `case "$prefix" in *[\"\$\\\ ]*) error "...";; esac`.

### IN-06: Documentation still states the old platform floor

**File:** `.planning/codebase/ARCHITECTURE.md:248` (outside the reviewed file
list, but directly affected by `default.rave:1`)
**Issue:** The document still says `APP_MIN_OS = 10.12`. The value in code is
now `26.7.1`.
**Fix:** Update the line to match `default.rave`, or reference the variable
rather than repeating the value.
